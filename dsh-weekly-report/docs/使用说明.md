## 1. 安装（两种方式，数据同一处）

两种方式装的是同一份代码；**数据（配置 / API Key / 日志 / 默认输出）永远在同一个用户目录**
`%USERPROFILE%\.dsh\weekly-report`，所以随时可以切换，不会出现「两套配置」。

**前置**：Windows、已装 DeepSeek Harness（DSH）、能访问 `github.com`。

### 1.1 方式 A · 本地检出 + Junction（推荐）

```powershell
# 检出仓库（路径建议 D:\Tools\Lau-tool）
git clone git@github.com:Lau-Jin/dsh-weekly-report.git D:\Tools\Lau-tool

# 注册到 DSH profile（Junction + dependencies + bundles + patch，均先备份）
powershell -ExecutionPolicy Bypass -File D:\Tools\Lau-tool\dsh-weekly-report\install.ps1

# 完全退出 DSH 再打开 → 侧边栏出现「周报」
```

脚本做的三件事（幂等、可重复执行）：

| 步骤 | 动作 |
|---|---|
| 1 | `%USERPROFILE%\.dsh\profiles\desktop\node_modules\dsh-weekly-report` 建 **Junction** → 仓库里的插件目录 |
| 2 | profile 的 `package.json`：`dependencies` 写 `link:<插件目录>`，`dsh.profile.bundles` 加 `dsh-weekly-report`（顺带去重） |
| 3 | profile 的 `cordis.patch.yml`：`insert weekly-report` |

**更新**：`cd D:\Tools\Lau-tool && git pull` → 重启 DSH。**不需要重装**。

| 参数 | 作用 |
|---|---|
| `-Status` | 看当前状态（Junction 指向、依赖写法、bundle、patch、服务进程、数据目录） |
| `-Uninstall` | 卸载（保留数据，需手动清） |
| `-Profile web` | 装到别的 profile（默认 `desktop`） |
| `-ProfileRoot <路径>` | 直接指定 profile 目录 |
| `-Copy` | 不用 Junction，复制一份（**代价**：改代码不即时生效） |

### 1.2 方式 B · DSH 插件页填仓库地址

DSH → 设置 → 插件 → **添加插件** → 填：

```
git@github.com:Lau-Jin/dsh-weekly-report.git
```

也可用 `https://github.com/Lau-Jin/dsh-weekly-report.git`。

> 仓库根目录有一个「入口包」`package.json`：`name` = `dsh-weekly-report`，
> `main` / `dsh.bundle.patch` / `exports("./client")` 都指向子目录 `dsh-weekly-report/`，
> 所以填裸仓库地址就能装出本插件。

- 装完**完全退出 DSH 再打开**
- **更新**：插件页点「更新」，或重新填一次地址（会重新解析默认分支最新 commit），再重启 DSH
- **卸载**：插件页「卸载」

### 1.3 两种方式怎么选

| | A · Junction | B · 插件页 |
|---|---|---|
| 插件实体 | 指向仓库目录 | 复制进 `node_modules` |
| 改代码 | **重启 DSH 即生效** | 要重装 |
| 更新 | `git pull` + 重启 | 点「更新」+ 重启 |
| 数据 | `%USERPROFILE%\.dsh\weekly-report` | 同左 |
| 适合 | 自己维护、要改引擎/界面 | 只想用、不折腾 |

### 1.4 判断当前是哪种

```powershell
powershell -ExecutionPolicy Bypass -File D:\Tools\Lau-tool\dsh-weekly-report\install.ps1 -Status
```

| 输出 | 结论 |
|---|---|
| `dependency : link:...` + `link : Junction -> ...` | 方式 A |
| `dependency : github:...`、`link : real directory` | 方式 B |

**切换**：先卸载（`install.ps1 -Uninstall` 或插件页卸载），再用另一种方式装。数据不受影响。

### 1.5 装完检查

```powershell
powershell -ExecutionPolicy Bypass -File D:\Tools\Lau-tool\dsh-weekly-report\install.ps1 -Status
```

面板内「概览」页有 7 项体检，全绿即可用。

## 2. 第一次使用

1. 侧边栏点「周报」→ **配置** 页
2. **API Key**：研发平台 → 个人设置 → API Key，粘贴 → `保存` → `测试`
   - 成功会提示「MCP 正常，可用工具 N 个（xxx ms）」
3. **生成参数**：确认 `处理人`（默认 张三）、`周报输出目录`、`绩效表目录`
4. **邮件通知**（可选）：开启 → 填 SMTP / 发件邮箱 / **客户端授权码** / 收件人 → 保存 → `试运行（不发信）`
5. 切到 **生成** 页 → 周期选「本周」→ 点「开始生成」

> 首次启动会自动从旧位置 `D:\Reports` **只读一次**迁移配置/Key（如果存在），
> 概览页会显示「迁移来源」。

## 3. 界面说明

### 概览
- **健康状态**：7 项体检（API Key / Python / 内置引擎 / 邮件 / 定时任务 / 绩效表目录 / 输出目录）
- **快捷操作**：生成本周 / 只试运行 / 查看历史
- **绩效表核对**：一键核对本月绩效表（对照本月各周周报，缺的自动补），下面直接显示报告
- **系统定时任务**：状态、下次运行、是否已接管；按钮「登记每周自动生成（周日 22:00）」/「移除定时任务」
- **最近一次生成**：成功/失败 + 时间 + 产物路径（默认隐藏）
- **路径**：默认隐藏（点「显示路径」才展开），定时任务 / 守护 / 最近一次生成里的路径跟着一起显隐
- **面板服务守护**：折叠在概览最底部，点「展开」才看状态与装/卸

### 配置
三张卡片 + 底部固定操作条：

| 卡片 | 内容 |
|---|---|
| 研发平台接入 | API Key（可切换明文）、测试、MCP 地址 |
| 生成参数 | 处理人、相似度阈值（滑块+数字）、输出目录、绩效表目录 |
| 邮件通知 | 开关、SMTP、端口、发件人、授权码、收件人 |

- **处理人不是过滤条件**：周报不只收「处理人是我」的工单，**本周期有我的工时记录**的工单也会计入。
  该字段用于：① 本周期新建工单是否算我的；② 跨周收尾是否算我的；③ 日志里「我处理」标记。
- **目录可点选**：`浏览…` 打开选择器，支持盘符、面包屑、单击选中/双击进入、新建文件夹。
- 改动后底部出现「有未保存修改」，点「保存配置」写入。

### 生成
- 周期：本周 / 上周 / 自定义（分隔控件）
- 选项：同时生成绩效 xlsx / 只试运行不发信 / 不读任务中心
- 日志卡片有状态条：灰点等待、蓝点闪烁生成中（显示已用时长）、绿点完成、红点失败
- 一次通常 1~3 分钟（平台限流 60 次/分钟），期间可「终止」

### 历史
扫描输出目录下所有 `周报_*.txt`，可搜索、可查看正文。

### 注意事项
15 条内置规则，可按「全部 / 注意 / 重要」筛选。

### 保持在线（连通性）
- 探活用 `GET /api/ping`（1~2 ms，不跑体检）；`/api/state` 改成内存缓存 + 后台刷新，第一次调用也是毫秒级
- 宿主 20 秒心跳探 ping，服务挂了自动拉起；面板/侧边栏也改成 ping，服务回来后自动刷新页面
- **面板服务守护**（计划任务 `周报面板守护`）：每 2 分钟探活，不在就拉起；DSH 关着、服务被杀都能回来
  - 概览「面板服务守护」卡片可一键装/卸；`install.ps1` 默认就装（`-NoWatchdog` 跳过）
  - 日志：`%USERPROFILE%\.dsh\weekly-report\logs\watchdog.log`
- 服务端口冲突（`port 8798 in use`）说明已有一份在跑，不需要再起


### 绩效表核对（概览页）
- 按钮「核对本月绩效表（缺的自动补）」：读本月各周周报文本 → 逐条比对当月绩效表 → 缺的补进去 → 报告写在表旁边 `*_核对.txt`
- 每周生成时会自动做一次；本周覆盖月末时就是月底核对
- 不需要 API Key，几秒钟出结果（只读周报目录和绩效表）

## 4. 生成规则（周报长什么样）

### 4.1 输出格式

每条目 6 行，字段前 2 个空格，条目间空一行：

```
【类别】
学校名称
  时间: 起-止
  事项: 工单标题
  工作内容：工单链接
  重要说明：无
  进度：xx%
```

### 4.2 纳入条件

| 条件 | 说明 |
|---|---|
| 本周期有我的工时 | **与处理人无关**，处理人是谁都算 |
| 本周期新建 且（处理人是我 或 关联任务我负责） | 新建即算本周工作 |
| 跨周收尾：本周期完成、处理人是我、且整张工单**零工时记录** | 本周完成但没记工时也算，时间取完成日 |

排除：已取消、补充工单（本周期新建但工时全在周期前）、批量补录（同一小时 ≥20 条我负责的新建任务且本周期无工时）。

### 4.3 进度与日期

| 情形 | 进度 | 时间 |
|---|---|---|
| 本周期有工时、周期后无新工时 | 100% | 本周期工时日期 |
| 本周期有工时、周期后还有工时 | 80% | 工时日期，**结束日拉到周日** |
| 状态已完成/已评分/待评分 + 完成日在本周期 | 100% | 完成日或工时区间 |
| 只有新建、无工时 | 按状态估算 10%~60% | 创建日~更新日（裁剪到周期内） |

### 4.4 子任务

- 父子**各自独立成条**，工时/时间各算各的
- 子任务未全部完成 → 父任务不算完成（进度最高 95%、有工时最低 60%）
- 父任务没我、子任务是我且有工时 → 子任务照常单列

**子任务怎么被发现的（重要）**：平台的「我的任务列表」接口**只返回顶层任务，不返回子任务**。
所以引擎对「本周期已纳入的父任务」会额外调一次详情拿 `children`，再逐个取子任务详情，判断：

| 判定依据 | 说明 |
|---|---|
| 负责人是我 / 参与人是我 | 子任务详情里的 `ownerUserId` 与 `assignees` |
| 本周期内新建 | 子任务 `createdAt` 落在周期内 |
| 本周期有我的工时 | 工时记录本身会带 `task_id`，这类子任务本来就会被单独拉取 |

- 学校优先取子任务标题里的学校（如「示例职业技术学院 示例产品_… 部署更新」），标题里没有才继承父任务
- 类型按子任务自己的标题判断（不继承父任务类型）
- **开销**：只对「本期已纳入的父任务」拉，每个父任务 1 次 + 每个子任务 1 次请求，最多 80 次；
  日志会打印「子任务补录：N 条（来自 X 个本期父任务，共 Y 次请求）」
- 例：工单 505「示例流程引擎更新」下有两个子任务（演示环境 / 示例职业技术学院），
  本周期新建、负责人是我 → 会各自单独出一条

### 4.5 重要说明

默认「无」。只有两种情况填：

1. 任务「风险预警」字段非空 → 填它
2. 本周期工时备注含 `重要 / 注意 / 风险 / 延期 / 阻塞 / 遗留 / 待跟进 / 紧急 / 重点 / 待确认`
   → 填该备注（最多 60 字）

> 想让某条进「重要说明」：在工时备注里带上关键词即可，例如 `注意：学校要求周五前完成`。

### 4.6 绩效表（月度考核表）怎么填

**一句话：当月绩效表 = 本月全部周报内容的合集，格式一点不动。**

| 规则 | 说明 |
|---|---|
| 每周并进去 | 生成周报时把本周条目并进当月表，先读表里已有的行再合并，不会冲掉前几周 |
| 同一事项一行 | 学校+事项相同就合并：起止时间取并集、「是否完成」取或、备注保留 |
| 只写六列 | 类别 / 学校+事项 / 开始时间 / 结束时间 / 是否完成 / 备注；其它单元格、合并区域、字体、行高一律不动 |
| 行数不够 | 自动下移「工作任务考核」等区块并校正 K4/M4 评分公式，版面还是原样 |
| 每周自动核对 | 对照本月各周周报逐条比对内容/时间/完成标记/格式，缺的补上 |
| 月底 | 本周覆盖月末时输出完整核对报告（表旁边 `*_核对.txt`）；上个月没核对过也会补一次 |

手动核对（不需要 API Key，也可以直接点面板上的按钮）：

```powershell
python "<repo>\dsh-weekly-report\service\engine\gen_weekly_text.py" `
  --config "%USERPROFILE%\.dsh\weekly-report\config.json" --perf-check --perf-fix
```

## 5. 邮件通知

| 字段 | 说明 |
|---|---|
| SMTP 服务器 | 163 用 `smtp.163.com` |
| 端口 | 465（SSL） |
| 发件邮箱 | 完整邮箱 |

## 6. 定时任务

概览页「登记每周自动生成（周日 22:00）」会创建/覆盖 Windows 计划任务 `周报自动生成`：

```
python.exe "<repo>\dsh-weekly-report\service\engine\gen_weekly_text.py"
  --config "%USERPROFILE%\.dsh\weekly-report\config.json"
  --week current --perf-auto --log
```

- 仍在你自己的任务计划程序里，可随时「移除定时任务」
- 不接管也能用，面板里手动生成一样
- 换了仓库路径后需要重新点一次「登记每周自动生成」

## 7. 数据存放在哪

**与安装方式无关**，统一在用户目录：

```
%USERPROFILE%\.dsh\weekly-report\
├── config.json    配置（含 SMTP 授权码）
├── api-key.txt    研发平台 API Key
├── reports\       默认周报输出目录
└── logs\          运行日志
```

| 内容 | 位置 |
|---|---|
| 配置 / API Key / 日志 / 默认输出 | `%USERPROFILE%\.dsh\weekly-report\` |
| 实际周报输出 | 面板「配置 → 周报输出目录」显示的位置 |
| 覆盖位置 | 环境变量 `WEEKLY_PANEL_DATA=<目录>` |

- 不在仓库里，所以换机器要重新填 Key（或从旧机器复制整个目录）
- 备份：直接复制 `%USERPROFILE%\.dsh\weekly-report`
- 卸载插件不会删它；确认不要了再手动删

## 8. 更新 / 发布

### 8.1 本机改代码 → 推送

```powershell
cd D:\Tools\Lau-tool
# 改文件……
powershell -ExecutionPolicy Bypass -File .\publish.ps1 -Message "说明这次改了什么"
```

`publish.ps1` 会：列改动 → 告警疑似凭据 → **bump 版本号** → commit → push。

### 8.2 别的机器更新

| 安装方式 | 更新做法 |
|---|---|
| A · Junction | `cd D:\Tools\Lau-tool && git pull` → 重启 DSH |
| B · 插件页 | 插件页点「更新」（或重新填一次地址）→ 重启 DSH |

都不需要重装、不会丢配置（数据在 `%USERPROFILE%\.dsh\weekly-report`）。

### 8.3 版本号约定

每次 `publish.ps1` 默认 `patch +1`（如 0.2.2 → 0.2.3）。
版本号会显示在面板 `/api/state` 与插件页，便于确认各机器是否同步。

## 9. 常见问题

| 现象 | 处理 |
|---|---|
| 侧边栏没有「周报」图标 | 确认 `install.ps1 -Status` 三项为真；**重启** DSH（不是刷新） |
| 面板显示「服务未响应」 | 面板服务没起：看 `%USERPROFILE%\.dsh\weekly-report\logs\panel.log`；host 半身会在 60 秒内自动拉起，也可手动 `node service\server.cjs` |
| 体检「Python 环境」红 | 需要带 `openpyxl` 的 Python；DSH 运行时自带（`~\.dsh\dsh-runtimes\...\python`） |
| 体检「内置引擎」红 | `service\engine\gen_weekly_text.py` 缺失，`git pull` 恢复 |
| 生成报「API Key 无效」 | 配置页重新粘贴 Key 并点「测试」 |
| 生成很慢 / 卡住 | 平台限流 60 次/分钟，一次 1~3 分钟正常；撞限会自动等 20 秒重试 |
| 邮件 535 认证失败 | 用了登录密码，需换成客户端授权码 |
| 周报少了某条 | 看生成日志「工单命中 / 任务中心命中」的计数；可能被「补充工单 / 批量补录 / 已取消」规则排除 |
| 进度不对 | 有工时取工时进度；没有按状态；子任务未完成父任务最高 95% |
| 换机器后配置没了 | 正常，数据在 `%USERPROFILE%\.dsh\weekly-report` 不入库；重新填 Key，或从旧机器复制整个目录 |
| 想彻底重装 | `install.ps1 -Uninstall` → 重启 DSH → `install.ps1` → 重启 DSH（数据保留） |
| 插件页报「包元信息错误 … package.json: ENOENT `<旧路径>`」 | 插件目录被移动过（换了检出位置），但 DSH 进程还持有旧路径。① 在旧路径建兼容 Junction：`mklink /J "<旧路径>" "<新路径>"`；② **完全退出 DSH 再打开**，旧路径引用就被丢掉，Junction 可留可删 |
| 迁移后插件图标消失 / 报找不到模块 | 同上：profile 的 `node_modules\dsh-weekly-report` Junction 与 `package.json` 里的 `link:` 必须指向**同一个**新路径；跑一次 `install.ps1` 会一起修好 |

## 10. 附录：安装方式与数据位置的关系

早期用「填地址安装」时，插件被复制进 `node_modules`，数据写在 `%USERPROFILE%\.dsh\weekly-report`；
Junction 版则把数据放在插件目录里。两种数据位置不同，同一台机器切换会出现「两套配置」，容易误以为配置丢了。

现在**数据目录固定**在 `%USERPROFILE%\.dsh\weekly-report`（可用 `WEEKLY_PANEL_DATA` 覆盖），
与安装方式解耦，所以：

- 两种方式随便切，配置 / Key / 历史都在
- 插件目录只是「代码」，删掉重装不丢数据
- 仓库里永远不会出现凭据（`service/data` 已不再使用，`.gitignore` 仍保留以防旧版本）

首次启动会自动迁移旧数据：

| 迁移顺序 | 来源 | 内容 |
|---|---|---|
| ① | `<插件>/service/data` | Junction 旧版本的配置 / Key / 日志 / 报告 |
| ② | `D:\Reports\weekly_config.json`、`api_key.txt` | 更早的桌面版 |

迁移是「不覆盖」策略：目标已存在同名文件就跳过。
